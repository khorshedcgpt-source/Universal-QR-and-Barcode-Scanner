# BARCODE SUPPORT SPECIFICATION

## Universal QR and Barcode Scanner

**Repository:** `Universal-QR-and-Barcode-Scanner`
**Document Status:** Pre-Implementation / Capability Specification
**Purpose:** Define exactly which barcode formats the application targets, their support status, limitations, and validation requirements.

---

# 1. Purpose

This document defines the barcode format support contract for the Universal QR and Barcode Scanner.

It prevents the application, documentation, or AI coding agents from claiming support for a barcode format merely because a scanner library lists that format.

A format is considered **supported by the application** only after:

1. The selected scanner engine supports it.
2. The target platform supports it.
3. The application integration works.
4. Representative test cases pass.
5. Important limitations are documented.
6. Accuracy is acceptable for the intended use.

---

# 2. Supported Format Groups

## 2.1 1D / Linear Formats

The initial target list is:

1. EAN-8
2. EAN-13
3. UPC-A
4. UPC-E
5. Code 39
6. Code 93
7. Code 128
8. ITF
9. Codabar

## 2.2 2D Formats

The initial target list is:

1. QR Code
2. Data Matrix
3. Aztec
4. PDF417
5. Micro QR

Micro QR is conditional and must not be advertised as supported until the final selected scanner engine and both target platforms have passed validation.

---

# 3. Support Status Definitions

Use the following statuses:

| Status      | Meaning                                                      |
| ----------- | ------------------------------------------------------------ |
| REQUIRED    | Mandatory target for V1                                      |
| SUPPORTED   | Verified on the relevant platform                            |
| CONDITIONAL | Supported only if selected engine/platform passes validation |
| TESTING     | Implementation exists but validation is incomplete           |
| LIMITED     | Supported with documented restrictions                       |
| UNSUPPORTED | Not available through the selected implementation            |
| DEFERRED    | Intentionally postponed                                      |
| FAILED      | Tested but did not meet acceptance criteria                  |

---

# 4. Platform Scope

The project targets:

* Android
* Web

A format may have different technical capabilities on different platforms.

Therefore support must be tracked independently:

```text
Format
 ├── Android
 └── Web
```

Do not use Android support as proof of Web support.

Do not use Web support as proof of Android support.

# 20. PDF417

## Status

**REQUIRED / CRITICAL for V1.**

PDF417 is a particularly important format for this project because of the project's Bangladesh National ID use case.

The scanner must treat PDF417 as a first-class format rather than an incidental format.

Google ML Kit explicitly supports PDF417 on Android.

---

# 21. PDF417 Is Not Automatically NID

This is a mandatory rule.

```text
PDF417 detected
       ≠
Bangladesh NID detected
```

PDF417 is a barcode symbology.

It can carry many kinds of data.

Therefore:

```text
PDF417 Detection
        ↓
Raw Payload
        ↓
Optional Format Identification
        ↓
Optional NID Parser
```

The application must not label every PDF417 barcode as a Bangladesh National ID.

# 23. Bangladesh NID-Oriented PDF417 Testing

NID-related testing must use:

* synthetic data
* anonymized fixtures
* legally approved test material

Do not commit:

* real NID number
* real name
* real address
* real date of birth
* real NID card image
* real raw NID payload

---

# 24. NID Parsing Must Be Separate

The implementation should conceptually separate:

```text
Scanner
   ↓
PDF417 Decoder
   ↓
Raw Payload
   ↓
NID Format Detector
   ↓
NID Parser
   ↓
Validation
   ↓
Structured Display
```

This allows the scanner to remain useful for ordinary PDF417 barcodes.

---

# 25. NID Payload Assumption Rule

The project must not assume a specific Bangladesh NID PDF417 payload structure unless that structure has been independently verified from an authoritative or appropriately validated technical source.

AI coding agents must not invent:

* field positions
* delimiters
* XML structure
* binary structure
* encoding
* checksum
* field names

based only on internet examples or guesses.

---

# 26. Character Encoding

PDF417 data may represent raw bytes or encoded text.

Therefore the NID parser must explicitly document:

* byte representation
* encoding detection
* supported encoding
* fallback behavior
* invalid byte handling
* normalization

A visually readable output is not sufficient proof that the encoding is correct.

---

# 27. NID Privacy Requirements

NID-related decoded information must be treated as highly sensitive.

The application must not:

* upload it automatically
* send it to analytics
* log it in production
* automatically copy it
* automatically share it
* expose it in debug telemetry
* store it permanently without an explicit product decision

Sensitive fields should be masked where appropriate.

---

# 28. MICRO QR

## Status

**CONDITIONAL.**

Micro QR must not be declared V1-supported until the selected production scanner engine and target platforms demonstrate reliable decoding.

Current ZXing-C++ documentation lists Micro QR Code support, while Google ML Kit's documented barcode formats do not include Micro QR.

Therefore the project must treat Micro QR as an engine-dependent capability.

## Acceptance Requirement

Micro QR can become:

```text
SUPPORTED
```

only after:

* Android test passes
* Web test passes
* camera test passes where applicable
* image test passes
* accuracy corpus passes
* performance is acceptable

Otherwise:

```text
CONDITIONAL / DEFERRED
```

# 33. Format Detection Rule

The UI must display the actual detected format returned by the scanner engine.

Do not infer:

```text
"PDF417 therefore NID"
```

or:

```text
"QR therefore URL"
```

A QR code can contain ordinary text.

A PDF417 can contain ordinary data.

Format and content type are separate concepts.
