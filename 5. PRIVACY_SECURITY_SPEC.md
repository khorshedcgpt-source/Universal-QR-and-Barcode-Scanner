# 1. Purpose

This document defines the privacy and security requirements for the Universal QR and Barcode Scanner.

The application is designed around the following security philosophy:

> **Process locally, collect minimally, store only what is necessary, and never transmit scan data without an explicit product requirement and appropriate user action.**

This specification is especially important because the scanner may decode:

* URLs
* personal information
* contact information
* authentication-related content
* payment-related content
* identification/document data
* PDF417 data
* potentially sensitive information contained in Bangladesh NID barcodes

---

# 2. Security Principles

The application must follow:

1. Privacy by design
2. Data minimization
3. Local-first processing
4. Least privilege
5. Secure defaults
6. Explicit user action
7. No unnecessary tracking
8. No unnecessary network communication
9. Safe handling of untrusted barcode content
10. Secure lifecycle management
11. Transparent data behavior
12. Defense in depth

---

# 3. Privacy Model

The default data flow must be:

```text
Camera / Image
      ↓
Local Processing
      ↓
Barcode Decoder
      ↓
Local Result
      ↓
Optional Local History
```

The default data flow must NOT be:

```text
Camera
   ↓
Internet
   ↓
Remote Server
   ↓
Barcode Decoder
```

---

# 4. No Mandatory Backend

Version 1 must not require a backend server for:

* barcode detection
* barcode decoding
* result classification
* history
* settings
* basic application functionality

The application must remain usable without:

* user registration
* login
* API key
* cloud account
* remote database
* cloud barcode-recognition API

---

# 5. Local Processing Requirement

Barcode decoding must occur locally.

This includes:

* camera scanning
* image scanning
* file scanning
* QR decoding
* 1D barcode decoding
* 2D barcode decoding
* PDF417 decoding

No decoded barcode content should be transmitted to a server for ordinary scanning.

---

# 6. Camera Privacy

Camera access is one of the application's most sensitive capabilities.

The application must:

* request camera access only when required
* stop camera processing when scanning ends
* release camera resources when leaving the scanner
* avoid recording video
* avoid storing camera frames by default
* avoid uploading camera frames
* avoid retaining frames longer than necessary

The camera should function as a temporary scanner input, not as a recording system.

---

# 7. Camera Frame Retention

Camera frames must normally exist only in memory for the duration required for scanning.

The application must not automatically:

* save frames
* create screenshots
* create video recordings
* cache camera images permanently
* add camera images to history

unless a future feature explicitly requires it.

---

# 8. Image/File Privacy

When the user selects an image:

```text
User selects image
       ↓
Local application processing
       ↓
Barcode decode
       ↓
Result
```

The original image must not be uploaded automatically.

After processing, unnecessary image data should be released.

---

# 9. File Access Minimization

The application should request access only to the selected file/image rather than broad filesystem access whenever platform APIs allow.

The application must not scan unrelated user files.

---

# 10. Microphone Privacy

The application does not require microphone access.

Microphone permission must not be requested.

---

# 11. Location Privacy

The application does not require location access for core scanning.

Location permission must not be requested.

A geographic barcode result may contain coordinates, but decoding such data does not justify requesting device location.

---

# 12. Contacts Privacy

The application does not require contacts permission for core scanning.

The application must not request contacts permission merely because a barcode contains contact information.

Creating a contact must always be a future, explicit, user-initiated feature.

---

# 13. Phone and SMS Permissions

The application must not request:

* phone permissions
* SMS permissions

merely to classify phone/SMS barcode content.

If future contextual actions are implemented, they should use the minimum platform capability necessary.

---

# 14. Network Privacy

Core scanning must work without network access.

The application should not make network requests for:

* barcode decoding
* QR decoding
* PDF417 decoding
* history search
* result classification
* settings
* basic application operation

---

# 15. Network Request Policy

Any network request introduced in the future must have:

1. A documented purpose
2. A defined destination
3. A defined data payload
4. A privacy justification
5. A security review
6. Appropriate user-facing disclosure

No AI coding agent may introduce arbitrary analytics, telemetry, tracking, or remote APIs.

---

# 16. External URLs

Decoded URLs are untrusted input.

The application must never assume that a scanned URL is safe.

Before opening:

```text
Decoded data
    ↓
URL parser
    ↓
Scheme validation
    ↓
Display destination
    ↓
User action
    ↓
External browser
```

---

# 17. Allowed URL Schemes

The default safe URL schemes should be:

```text
https:
http:
```

Other schemes must not be opened automatically.

Potentially sensitive schemes such as:

```text
javascript:
data:
file:
intent:
custom application schemes
```

must be handled explicitly and conservatively.

---

# 18. Automatic Execution Prohibited

Decoded content must never be executed as code.

The application must not:

* execute JavaScript from QR content
* interpret barcode data as application commands
* automatically install software
* automatically open arbitrary local files
* automatically execute shell commands
* automatically connect to services

Barcode content is always untrusted data.

---

# 19. HTML Injection Protection

Decoded text must be treated as plain text by default.

The application must not insert decoded barcode content into the DOM as raw HTML.

For example:

```text
Unsafe:
decodedContent → innerHTML
```

must be avoided.

Use safe text rendering.

---

# 20. URL Display Safety

Long URLs should be displayed in a readable form while preserving the complete value.

The user should be able to inspect the full URL before opening it when appropriate.

The UI must not disguise the destination in a misleading way.

---

# 21. Redirect Awareness

A scanned URL may redirect to another destination.

The scanner cannot guarantee the safety of the final website.

The application should therefore avoid presenting:

> "This website is safe."

unless a future security service provides a documented basis for such a claim.

The application should instead communicate the destination clearly.

Examples:

Classification must not automatically trigger the corresponding action.

# 23. Sensitive Data Classification

Potentially sensitive data includes:

* national identification information
* personal identification numbers
* date of birth
* address
* phone numbers
* email addresses
* authentication credentials
* Wi-Fi passwords
* payment-related data
* private URLs
* personal contact records

The application must treat decoded content as potentially sensitive even if it cannot identify the exact data type.

---

# 24. Bangladesh NID PDF417

The application may be used to decode PDF417 data appearing on Bangladesh National Identity Cards.

For privacy purposes, NID-related barcode content must be treated as **highly sensitive personal data**.

The application must therefore:

* process it locally
* avoid network transmission
* avoid analytics collection
* avoid raw-content logging
* avoid automatic sharing
* avoid automatic copying
* avoid automatic external actions
* avoid storing original NID images by default

---

# 25. NID Payload Parsing

The exact internal structure of Bangladesh NID PDF417 data must not be assumed without verified technical evidence.

Therefore the parser architecture must distinguish:

```text
Raw PDF417 payload
        ↓
Format detection
        ↓
Payload parser
        ↓
Validation
        ↓
Structured fields
```

The parser must not invent fields.

If a payload cannot be reliably interpreted:

```text
Unknown / Raw PDF417 Data
```

should be shown instead of making unsupported assumptions.

---

# 26. NID Structured Data

If a payload is successfully parsed into structured fields, the application may display only fields that are:

1. Actually present
2. Successfully decoded
3. Validated against the known format
4. Supported by the application's parser

Example:

```text
Name
Date of Birth
Address
Identification Number
```

must not be displayed unless those fields are actually available and reliably identified.

---

# 27. Character Encoding

Barcode payloads may contain different character encodings.

The application should use an explicit decoding strategy rather than blindly assuming UTF-8.

Possible decoding stages:

```text
Raw bytes
   ↓
Encoding detection / known format
   ↓
Character decoding
   ↓
Validation
   ↓
Text
```

The exact encoding rules for Bangladesh NID payloads must be established from verified authorized test data before being treated as a fixed requirement.

---

# 28. Raw Payload Security

Raw barcode payloads must be treated as sensitive until classification determines otherwise.

They must not be:

* written to production logs
* sent to analytics
* included in crash reports
* inserted into URLs without validation
* stored in debugging tools unnecessarily

---

# 29. History Privacy

History is optional local user data.

If history is enabled:

```text
Scan Result
     ↓
Local Storage
```

No remote history database should exist in Version 1.

---

# 30. History Data Minimization

Only information required for the history feature should be stored.

The application should avoid storing:

* camera frames
* source images
* full document scans
* unnecessary metadata
* device identifiers
* location data

---

# 31. History Sensitive Data

Because history may contain sensitive information, the UI should avoid unnecessarily exposing complete content in list previews.

Example:

```text
PDF417
Personal identification data
24 Sep 2026
```

is preferable to exposing an entire sensitive payload in a list.

---

# 32. History Search

History search must be local.

Search must not send the user's scan history to:

* a search engine
* analytics service
* cloud database
* external API

---

# 33. History Deletion

Users must be able to delete history.

Required operations:

```text
Delete one item
Clear all history
```

Deletion confirmation should be required for destructive bulk operations.

---

# 34. Secure Deletion

Application-level deletion means removing the data from the application's managed storage.

The application must not claim that ordinary deletion guarantees forensic destruction from every possible underlying storage layer.

User-facing documentation should use accurate terminology.

---

# 35. Clipboard Privacy

Copy is a user-initiated operation.

The application must not automatically copy scan results to the clipboard.

This is particularly important for:

* NID data
* passwords
* Wi-Fi credentials
* private URLs
* authentication tokens

---

# 36. Clipboard Feedback

After copying:

```text
Copied to clipboard
```

may be displayed.

The application should not retain a second internal copy solely for clipboard functionality.

---

# 37. Sharing Privacy

Sharing must always be initiated by the user.

The application should use the operating system's normal share mechanism where possible.

Before sharing highly sensitive structured data, a warning may be displayed.

Example:

```text
This result may contain personal information.

Share anyway?

[Cancel] [Share]
```

---

# 38. Screenshot Considerations

The application should avoid intentionally exposing sensitive information through unnecessary UI elements.

Future Android-specific security features may be considered for especially sensitive screens, but such features must not be enabled without evaluating their usability implications.

---

# 39. Logging Policy

## Development

Debug logs may include:

* lifecycle events
* scanner initialization status
* performance measurements
* error categories

## Production

Logs must not contain:

* complete barcode contents
* NID payloads
* passwords
* Wi-Fi credentials
* private URLs
* personal information
* image data

---

# 40. Crash Reporting

A crash-reporting service must not be added by default.

If introduced in the future:

* privacy impact must be reviewed
* sensitive fields must be scrubbed
* raw scan content must be excluded
* camera frames must not be attached
* users must be informed appropriately

---

# 41. Analytics

Version 1 should not include third-party behavioral analytics by default.

The project must not silently introduce:

* Google Analytics
* advertising identifiers
* tracking pixels
* session replay
* fingerprinting
* cross-site tracking

unless a future product decision explicitly introduces them and the privacy specification is updated.

---

# 42. Advertising

Advertising SDKs are out of scope for Version 1.

No advertisement system should be added to the scanner without a separate product, privacy, security, and UX review.

---

# 43. Device Identifiers

The application must not collect device identifiers for core scanning.

Avoid unnecessary collection of:

* IMEI
* Android advertising ID
* hardware serial number
* persistent device identifier
* IP address for application analytics

---

# 44. User Accounts

Version 1 does not require accounts.

No:

* username
* password
* email registration
* authentication server

is required for core functionality.

---

# 45. Authentication

There is no authentication requirement for ordinary local scanning.

If a future feature introduces protected local data, an explicit authentication/security design must be created before implementation.

---

# 46. Local Storage Security

IndexedDB is the primary local storage mechanism for Web/PWA data.

The application must recognize that browser-managed local storage is not equivalent to a hardware-backed secure vault.

Therefore:

* minimize sensitive storage
* do not store secrets unnecessarily
* do not claim military-grade encryption without implementation evidence
* document the actual protection model

---

# 47. Sensitive Data at Rest

The application should avoid retaining highly sensitive decoded data unless history functionality requires it.

If future requirements demand stronger protection, an encrypted local-storage design must be evaluated separately.

Potential approaches may include:

* Web Crypto
* Android Keystore-backed encryption
* platform-specific secure storage

No encryption mechanism should be added merely as a marketing claim.

---

# 48. Encryption

If sensitive data is transmitted in a future feature:

* TLS must be mandatory
* certificate/security configuration must be appropriate
* plaintext HTTP must not be used for sensitive transmission

However, Version 1 should avoid transmission altogether for core scanning.

---

# 49. Web Security

The Web application should use:

* HTTPS in production
* secure deployment configuration
* appropriate Content Security Policy where practical
* safe DOM rendering
* dependency auditing
* secure service-worker configuration

---

# 50. Content Security Policy

A future production Web deployment should define a restrictive Content Security Policy appropriate for:

* React application
* WebAssembly scanner
* local assets
* camera access
* required application functionality

The CSP must not be weakened simply to make an unsafe third-party script work.

---

# 51. WebAssembly Security

The ZXing-C++ WebAssembly module must be treated as application code.

Requirements:

* bundle or serve from a controlled application origin
* verify dependency provenance
* avoid arbitrary remote WASM execution
* keep the WASM module version controlled
* update it deliberately

---

# 52. Service Worker Security

The PWA service worker must cache only trusted application assets.

It must not:

* cache arbitrary decoded URLs
* intercept unrelated websites
* upload scan content
* create hidden network synchronization
* store unnecessary sensitive data

---

# 53. Android Security

The Android application should:

* use modern Android security practices
* minimize permissions
* avoid unnecessary exported components
* avoid unnecessary native capabilities
* keep dependencies updated
* use release signing correctly

---

# 54. Native Bridge Security

Any Capacitor/native bridge must expose the minimum required functionality.

For example:

```text
React
  ↓
Scanner Plugin
  ↓
Native Scanner
```

The native plugin should not expose broad filesystem or system capabilities when only camera scanning is required.

---

# 55. Native Input Validation

Data crossing:

```text
JavaScript ↔ Native
```

must be validated.

Do not trust JavaScript-provided values merely because they originate from the application UI.

Native methods should validate:

* format identifiers
* image dimensions
* scan configuration
* file paths/URIs
* command parameters

---

# 56. File Path Security

The application must not blindly open arbitrary file paths from decoded barcode content.

Decoded strings must never be interpreted as trusted local filesystem paths.

---

# 57. Intent Security

On Android, decoded content must not automatically create arbitrary intents.

If a future contextual action launches an Android intent:

* allowed actions must be restricted
* input must be validated
* user initiation must be required

---

# 58. Deep Links

Future deep-link support must validate incoming parameters.

A deep link must never automatically execute a sensitive scanner operation.

---

# 59. Supply Chain Security

Dependencies must be reviewed for:

* known vulnerabilities
* maintenance status
* license
* provenance
* unnecessary permissions
* suspicious install scripts

Lockfiles must be committed.

---

# 60. Dependency Updates

Security updates should be applied deliberately.

A dependency must not be upgraded automatically if the upgrade could:

* break scanner accuracy
* change supported formats
* change privacy behavior
* change storage behavior
* change platform permissions

Scanner fixture tests must be run after scanner-engine updates.

---

# 61. Scanner Engine Security

The scanner engine processes untrusted image/data input.

Therefore:

* keep the engine updated
* test malformed inputs
* test oversized images
* test corrupted images
* test unusual barcode content
* monitor security advisories
* avoid unsafe native bindings

---

# 62. Malformed Input Handling

The application must safely handle:

* corrupted images
* extremely large images
* invalid PDF417 data
* malformed QR payloads
* unexpected byte sequences
* empty results
* unusual metadata

Malformed input must result in a controlled error, not application termination.

---

# 63. Resource Exhaustion

The scanner must protect against excessive resource consumption.

Controls may include:

* maximum image dimensions
* frame throttling
* decode timeouts
* memory limits
* result limits
* input-size validation

The exact limits should be determined during implementation and testing.

---

# 64. Denial-of-Service Consideration

Although this is primarily an offline client application, malicious files/images could attempt to consume excessive resources.

The application should therefore reject or constrain unreasonable inputs.

---

# 65. Privacy-Preserving Error Messages

User-facing errors must not reveal unnecessary sensitive data.

Avoid:

```text
Failed to parse NID payload:
[entire personal payload]
```

Prefer:

```text
The barcode data could not be interpreted.
```

---

# 66. Debug Mode

If a developer/debug mode is introduced, it must clearly warn that additional diagnostic information may be displayed.

Sensitive data should still be redacted by default.

A debug switch must not automatically disable privacy protections.

---

# 67. Test Data Privacy

Test fixtures must not contain real personal information unless there is a documented legal and security reason.

For NID/PDF417 testing:

```text
Preferred:
Synthetic data
Anonymized data
Authorized test samples
```

Avoid:

```text
Real person's NID
Real NID number
Real address
Real date of birth
Real personal records
```

```text
          ┌────────────▼────────────┐

                       │

                       │
          ┌────────────▼────────────┐

          └────────────┬────────────┘
                       │
                 Raw Result
                       │
          ┌────────────▼────────────┐
          │ Classification/Parser  │
          └────────────┬────────────┘
                       │
                  Validation
                       │
          ┌────────────▼────────────┐
          │     Safe Result         │
          └────────────┬────────────┘
                       │
            ┌──────────┼───────────┐
            ↓          ↓           ↓
         Display     History     User Action
                                  │
                                  ↓

```

# 94. Security Boundary Principle

The most important boundary is:

```text
Decoded Data ≠ Trusted Data
```

A barcode may contain syntactically valid data that is still malicious or unsafe.

Every external action must therefore occur after validation and explicit user initiation.

14. Never commit real personal test data.
15. Preserve the local-first privacy architecture.

# 100. Privacy Change Control

Any change involving:

* data collection
* storage
* transmission
* permissions
* external services
* analytics
* crash reporting
* authentication
* cloud synchronization
* NID parsing

requires review of this document before implementation.

---

# 101. Final Privacy Principle

The application should follow:

```text
Collect less
     ↓
Process locally
     ↓
Store less
     ↓
Share only by user action
     ↓
Transmit only when explicitly required
```

The core scanner should work without knowing:

* who the user is
* where the user is
* what other applications they use
* what files they own
* what websites they visit

The application should need only the information required to perform the scanning task.

---

# 102. Final Security Principle

The project must assume:

> **Every barcode, QR code, PDF417 payload, image, file, URL, and imported record is untrusted input until validated.**

This principle applies to ordinary QR codes as well as potentially sensitive identification-document barcodes.
