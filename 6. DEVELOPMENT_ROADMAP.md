# DEVELOPMENT ROADMAP

## Universal QR and Barcode Scanner

**Repository:** `Universal-QR-and-Barcode-Scanner`
**Project Description:** An accuracy-first, privacy-focused QR & barcode scanner supporting multiple 1D and 2D formats, built for Android and Web.

**Document Status:** Planning / Pre-Implementation
**Development Authority:** This document defines the approved development sequence and release gates.
**Source of Truth:** `PROJECT_SPECIFICATION.md`, `ARCHITECTURE.md`, `TECHNICAL_SPECIFICATION.md`, `UI_UX_SPECIFICATION.md`, and `PRIVACY_SECURITY_SPEC.md`

---

# 1. Purpose

This document defines the controlled development roadmap for the Universal QR and Barcode Scanner project.

The roadmap exists to prevent premature implementation, uncontrolled feature expansion, architecture drift, privacy violations, and accuracy regressions.

Development must proceed through clearly defined phases.

An AI coding agent must **not attempt to build the entire application in one step**.

Each phase must have:

* defined objectives
* approved inputs
* implementation scope
* validation requirements
* entry criteria
* exit criteria
* testing requirements
* documentation requirements

---

# 2. Core Development Principles

The project follows these principles throughout development:

1. Accuracy before feature quantity.
2. Privacy before convenience.
3. Offline functionality before cloud functionality.
4. Architecture before implementation.
5. Evidence before assumptions.
6. Tests before release.
7. Small changes before large changes.
8. Modular components before tightly coupled implementations.
9. User-controlled actions before automatic actions.
10. No silent requirement changes.
11. No unnecessary permissions.
12. No unnecessary network communication.
13. No real personal data in the repository.
14. No premature optimization without measurements.
15. No release without passing the defined quality gates.

# 7. Phase 1 — Technology & Architecture Verification

## Objective

Verify that the selected technologies can satisfy the project's requirements before building the real scanner.

## Activities

Verify:

* Android camera capability
* Web camera capability
* selected scanner engine
* supported barcode formats
* PDF417 support
* image/file scanning capability
* offline operation
* local storage mechanism
* platform integration
* build tooling
* browser compatibility
* Android compatibility
* performance constraints
* licensing requirements

## Scanner Engine Verification

The scanner engine approved in `TECHNICAL_SPECIFICATION.md` must be tested independently before being integrated into the complete application.

Do not assume that a library's advertised format support automatically means acceptable real-world accuracy.

## Required Questions

For the selected scanner engine:

* Does it decode the required 1D formats?
* Does it decode the required 2D formats?
* Does it decode PDF417?
* Does it support difficult images?
* Does it support camera frames?
* Does it support image/file input?
* Can decoding happen fully offline?
* Can decoding be controlled or throttled?
* Can scanner failures be distinguished from application errors?
* Is the license compatible with the intended distribution?
* Are Android and Web capabilities equivalent or different?

## Deliverable

Create Architecture Decision Records where a technology decision has meaningful trade-offs.

Example:

```text
ADR-001 Scanner Engine Selection
ADR-002 Android Camera Pipeline
ADR-003 Web Camera Pipeline
ADR-004 Local Storage Strategy
ADR-005 PDF417 Processing Strategy
```

## Exit Criteria

Technology choices are verified against actual project requirements.

# 9. Phase 3 — Shared Domain & Result Model

## Objective

Create the platform-independent data model shared by Android and Web.

## Core Concept

The scanner should produce a normalized result model rather than exposing platform-specific scanner objects directly to the UI.

Conceptually:

```text
Scanner Engine
      ↓
Raw Scan Result
      ↓
Normalized Scan Result
      ↓
Classification
      ↓
Application UI
```

## Result Model Should Support

Examples include:

* format
* raw payload
* decoded text
* byte data where applicable
* timestamp
* scan source
* confidence/metadata if available
* structured data where safely supported
* parsing status
* validation status

## Important Rule

Raw decoded data must remain distinguishable from interpreted data.

For example:

```text
Raw PDF417 payload
        ↓
Parser
        ↓
Structured interpretation
```

The application must not silently present an interpretation as if it were the original barcode payload.

## Exit Criteria

Android and Web can consume the same conceptual result model.

# 15. NID Data Handling Boundary

NID-related data is highly sensitive.

Development must therefore separate:

```text
Barcode decoding
```

from:

```text
NID payload interpretation
```

and:

```text
NID field presentation
```

Each stage must have independent tests.

---

# 16. NID Test Data Policy

Real National ID card images, raw payloads, names, NID numbers, dates of birth, addresses, or other personally identifiable information must not be committed to the repository.

Use:

* synthetic test data
* officially documented public test examples where legally appropriate
* anonymized fixtures
* developer-created mock payloads

If the exact payload structure is not officially verified, do not invent a parser and present it as authoritative.

---

# 17. NID Parsing Pipeline

If NID-specific interpretation is implemented, use the following conceptual pipeline:

```text
PDF417 Decode
      ↓
Raw Payload
      ↓
Encoding Detection / Normalization
      ↓
Format Identification
      ↓
Parser
      ↓
Validation
      ↓
Structured Fields
      ↓
Privacy-Safe Presentation
```

Every transformation should be testable independently.

---

# 18. Character Encoding Validation

PDF417 payloads may contain encoded byte data.

Encoding behavior must therefore be explicitly verified.

Do not randomly convert bytes using an assumed encoding simply because the output appears readable.

The implementation must document:

* input representation
* byte-to-text conversion
* supported encodings
* fallback behavior
* invalid-byte behavior
* normalization rules

If the actual encoding cannot be verified, the raw payload should remain available internally for controlled debugging while sensitive logging remains disabled in production.

# 55. First Coding Milestone

The first actual coding milestone should **not** be:

```text
Build the complete application.
```

It should be a controlled proof-of-concept.

Recommended sequence:

```text
Repository Preparation
        ↓
Technology Verification
        ↓
Scanner Engine POC
        ↓
Accuracy Test Corpus
        ↓
Shared Result Model
        ↓
Web Scanner
        ↓
Android Scanner
```

This sequence reduces the risk of building a large application around an unsuitable scanner implementation.

The roadmap is successful when the project can demonstrate:

2. Architecture is documented.
3. Technology decisions are justified.
4. Scanner-engine capability is proven.
5. Supported formats are tested.
6. PDF417 is separately validated.
7. NID interpretation is treated as a sensitive, independently tested layer.
8. Android and Web share a coherent domain model.
9. Core scanning works offline.
10. Results are handled safely.
11. History is locally controlled.
12. Privacy requirements are verifiable.
13. Security requirements are tested.
14. Accessibility is included.
15. Performance is measured.
16. Releases are versioned.
17. AI development is controlled.
18. No major requirement is silently changed.

# 57. Final Development Principle

The Universal QR and Barcode Scanner must be developed as a **measured engineering system**, not as a one-shot AI-generated application.

The development order is intentionally:

```text
SPECIFY
   ↓
ARCHITECT
   ↓
VERIFY TECHNOLOGY
   ↓
PROVE SCANNER
   ↓
MODEL DATA
   ↓
IMPLEMENT PLATFORM
   ↓
VALIDATE ACCURACY
   ↓
SECURE
   ↓
OPTIMIZE
   ↓
TEST
   ↓
BETA
   ↓
RELEASE
```

Accuracy, privacy, reliability, and maintainability take priority over rapid feature expansion.
