# TECHNOLOGY DECISIONS

## Universal QR and Barcode Scanner

**Project:** Universal QR and Barcode Scanner
**Platforms:** Android + Web
**Development Philosophy:** Accuracy-First, Privacy-First, Offline-First
**Document Status:** Technology Evaluation & Decision Record
**Implementation Status:** Not Yet Authorized

---

# 1. PURPOSE

This document records the major technology decisions, technology evaluations, trade-offs, verification requirements, and approved technical directions for the Universal QR and Barcode Scanner project.

The purpose is to prevent undocumented technology choices during implementation.

This document does **not** authorize production implementation by itself.

---

# 2. DECISION PRINCIPLES

All technology decisions must follow these priorities:

1. Accuracy
2. Privacy
3. Reliability
4. Offline capability
5. Platform compatibility
6. Performance
7. Maintainability
8. Security
9. Licensing
10. Implementation simplicity

Convenience alone must not determine technology selection.

A technically convenient library must not be selected if it materially reduces scanning accuracy, format coverage, privacy, or reliability.

---

# 3. TARGET PLATFORMS

The project targets:

```text
Android
Web
```

Android and Web must be evaluated independently where platform capabilities differ.

A single technology should only be shared when doing so provides a meaningful benefit without compromising platform-specific reliability.

# 5. CRITICAL TECHNICAL REQUIREMENT — PDF417

PDF417 is a high-priority requirement.

The scanner technology must demonstrate reliable PDF417 detection and decoding before production scanner implementation is approved.

The following must be evaluated:

* Standard PDF417
* Small PDF417
* High-density PDF417
* Low-resolution PDF417
* Blur
* Glare
* Rotation
* Perspective distortion
* Damaged PDF417
* Different camera qualities
* Image/file scanning
* Multiple PDF417 codes

---

# 6. BANGLADESH NID BOUNDARY

The application may eventually support workflows involving Bangladesh National ID cards.

However:

> **PDF417 is a barcode format, not an NID identifier.**

The scanner engine must first decode PDF417 generically.

NID-specific processing must be a separate domain layer.

Conceptual architecture:

```text id="y1uv6e"
Scanner Engine
      ↓
PDF417 Decoder
      ↓
Raw Payload
      ↓
Encoding Verification
      ↓
Structure Detection
      ↓
NID Parser
      ↓
Validation
      ↓
Structured Result
```

No NID payload structure may be invented or assumed.

Any NID-specific parser requires verified technical evidence.

Camera technology is critical to scanning accuracy.

The project must evaluate:

* Autofocus
* Torch

* Frame analysis
* Lifecycle handling

## Web

---

# 15. IMAGE PROCESSING

The project must evaluate whether preprocessing is necessary.

Potential processing techniques include:

* Resizing
* Cropping
* Grayscale conversion
* Contrast adjustment
* Sharpening
* Rotation correction
* Perspective correction
* Region-of-interest detection

However:

> Preprocessing must not automatically be added merely because it sounds useful.

Each preprocessing step should be evaluated against:

* Accuracy
* False positives
* False negatives
* Processing time
* Memory consumption
* Battery usage
* Format-specific behavior

Unnecessary preprocessing should be avoided.

---

# 16. LOCAL STORAGE

The application requires local storage for features such as scan history.

Evaluate:

* Browser storage
* IndexedDB
* Android local database
* Shared storage abstraction
* Encryption requirements
* Data migration
* Backup/import
* Storage limits
* Sensitive-data handling

Storage selection must support offline-first operation.

# 17. STATE MANAGEMENT

State management should remain as simple as practical.

Evaluate whether the application actually requires:

* Local component state

# 18. OFFLINE ARCHITECTURE

Core scanning must not depend on an internet connection.

Conceptual requirement:

```text id="y82u6n"
Camera / Image
       ↓
Local Scanner Engine
       ↓
Local Result
       ↓
Local History
```

Internet connectivity must not be required for core scanning.

Any future online functionality must have a separately documented requirement and privacy review.

---

# 22. SECURITY ARCHITECTURE

Security-sensitive boundaries include:

```text id="4m7d1p"
Camera Input
     ↓
Image Processing
     ↓
Scanner Engine
     ↓
Raw Barcode Data
     ↓
Validation
     ↓
Result Presentation
     ↓
External Actions
```

Each boundary must validate data appropriately.

Decoded content must never be treated as executable code.

---

# 23. URL HANDLING

Barcode content may contain URLs.

URLs must be treated as untrusted input.

The application must:

* Detect URLs
* Display them clearly
* Validate allowed schemes
* Avoid automatic opening
* Require explicit user action

Dangerous or unsupported schemes must not be executed automatically.

---

# 24. NID DATA SECURITY

NID-related data must receive stronger protection than ordinary barcode content.

The architecture should minimize:

* Storage
* Logging
* Network transmission
* Analytics
* Sharing
* Clipboard exposure

Real NID data must not be used in public test fixtures.

* Raw payload extraction

* Low resolution
* Blur
* Glare
* Rotation

* Damaged code

* Image input

---

# 39. MICRO QR DECISION

Micro QR is conditional.

It should only be marked as supported if:

1. The selected scanner engine supports it.
2. Android implementation supports it.
3. Web implementation supports it where required.
4. Accuracy is validated.
5. Test fixtures exist.

If these conditions are not met, Micro QR should remain conditional or deferred rather than falsely advertised as supported.

---

# 40. TECHNOLOGY DECISION PRINCIPLE

A technology is not considered production-ready merely because:

* It is popular
* It is easy to install
* An AI agent recommends it
* Documentation says it supports a format
* A sample project works
* One test image scans successfully

Production readiness requires appropriate verification.

# 41. AI CODING AGENT RULES

AI coding agents must:

* Read the project documentation
* Read this technology decision document
* Respect approved decisions
* Not replace approved technologies without approval
* Not introduce unnecessary dependencies
* Not silently change scanner engines
* Not silently change camera architecture
* Not bypass POC requirements
* Not claim unverified format support
* Not invent NID specifications
* Not claim tests passed without execution

If a technical decision is marked `UNDER INVESTIGATION` or `POC REQUIRED`, the agent must not silently treat it as `APPROVED`.

# 44. SCANNER ENGINE POC SCOPE

The POC should remain intentionally small.

It should answer:

> Can the selected scanner-engine technology reliably decode the required barcode formats on the target platforms under representative conditions?

The POC should not contain:

* Full application navigation
* Complete history
* Complete settings
* User accounts
* Production UI
* Cloud backend
* Analytics
* Full NID application logic

The POC exists only to validate the scanning technology.

---

# 45. POC SUCCESS CRITERIA

The POC should demonstrate:

* Required barcode detection
* Required barcode decoding
* PDF417 decoding
* Camera input
* Image input where applicable
* Android functionality
* Web functionality where applicable
* Offline processing
* Repeatable results
* No unnecessary network transmission

Accuracy results must be documented.
