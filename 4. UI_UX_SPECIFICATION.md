# 1. Purpose

This document defines the user interface, user experience, interaction behavior, navigation model, visual hierarchy, responsive behavior, accessibility requirements, scanner interaction, result presentation, history interface, settings interface, and error-state behavior of the Universal QR and Barcode Scanner.

This document defines **how the user experiences the application**.

It does not define implementation code.

---

# 2. Design Principles

The UI must follow these principles:

1. Simple
2. Fast
3. Accurate
4. Privacy-focused
5. Offline-first
6. Accessible
7. Responsive
8. Predictable
9. Minimal distraction
10. Clear feedback
11. Safe external actions
12. Consistent across Android and Web

The scanner should feel like a dedicated scanning utility rather than a general-purpose application overloaded with features.

---

# 3. Primary User Goals

The user should be able to:

1. Open the application.
2. Start scanning immediately.
3. Point the camera at a QR/barcode.
4. Receive a clear result.
5. Copy the result.
6. Share the result.
7. Open supported content safely.
8. Scan an image/file.
9. View previous scans.
10. Search history.
11. Delete history.
12. Change relevant scanner settings.

The most common workflow should require the fewest possible interactions.

# 8. Camera Preview

The camera preview should occupy the majority of the scanner screen.

Requirements:

* Maintain correct aspect ratio.
* Avoid unnecessary distortion.
* Prefer rear camera where available.
* Clearly communicate camera state.
* Stop camera processing when leaving the scanner.
* Resume appropriately when returning.

The preview must not continue consuming camera resources when the scanner is inactive.

---

# 9. Scan Overlay

The scan overlay should visually communicate where the user should position the barcode.

It should:

* remain clearly visible
* avoid excessive decoration
* work in light and dark environments
* provide sufficient contrast
* not permanently obscure the barcode
* adapt to different screen sizes

The overlay is guidance only.

The scanner must not be technically restricted to the visible box unless explicitly configured.

---

# 10. Scanner Status

The scanner should communicate its current state.

Possible states:

```text
Initializing
Camera permission required
Camera unavailable
Ready to scan
Scanning
Barcode detected
Processing
Result found
No barcode found
Scanner error
```

The user should never have to guess whether the camera is actually scanning.

```text
Initialize scanner
```

A lightweight loading indicator may be displayed during initialization.

The application should avoid unnecessary full-screen loading screens.

# 13. Permission Denied

If the user denies camera permission:

* Explain the consequence.
* Do not repeatedly request permission without user action.
* Provide an image/file scanning alternative.
* Provide a Settings option when supported by the platform.

Example:

```text
Camera access is unavailable.

You can:
[ Open Settings ]
[ Scan an Image ]
```

# 14. Torch Control

When the device supports torch/flash control, the scanner should provide a visible control.

States:

```text
Torch Off
Torch On
Unavailable
```

The application must not assume torch availability.

Torch control should be hidden or disabled when unavailable.

# 15. Camera Switching

If multiple cameras are available, the application may provide:

```text
Switch Camera
```

The rear camera should be preferred for barcode scanning.

Front camera support is optional for Version 1 but the architecture should not prevent it.

# 16. Image Scanning

The scanner must provide a clear alternative to camera scanning.

Possible action:


The user may:

* select an image
* upload a file
* drag and drop an image on Web where supported

No image should be uploaded to a remote server for decoding.

# 20. NID-Specific UX Boundary

The UI must distinguish between:

```text
PDF417 format
```

and:

```text
Bangladesh NID data
```

A PDF417 barcode does not automatically mean that it contains Bangladesh NID information.

Therefore the UI must not display:

> "Bangladesh NID detected"

unless the decoded payload has passed an explicitly defined and validated NID-format identification process.

---

# 21. NID Data Privacy

If a PDF417 contains personal identification information:

* display only what is necessary
* do not automatically transmit it
* do not automatically share it
* do not expose it in debug logs
* do not automatically save the original barcode image
* do not automatically open external services

Any sensitive-data interpretation must remain local.

# 22. Scan Success Feedback

When a barcode is successfully decoded:

```text
Camera
  ↓
Detection
  ↓
Short visual feedback
  ↓
Result
```

Feedback may include:

* subtle animation
* sound if enabled
* vibration on Android if enabled
* immediate result transition

The feedback must be short and must not significantly delay result presentation.

---

# 23. Duplicate Detection Feedback

When the same barcode remains in view:

The application should not repeatedly create results.

Possible behavior:

```text
Barcode detected
      ↓
Result shown
      ↓
Scanner paused
```

or:

```text
Barcode detected
      ↓
Result shown
      ↓
Duplicate suppressed
```

The exact behavior depends on the selected scan mode.

# 27. Copy Action

The Copy button should:

* copy the relevant result
* provide immediate feedback
* remain accessible
* avoid unnecessary confirmation dialogs

Example:

```text

```

A short confirmation is sufficient.

# 28. Share Action

The Share action should use the platform's normal share mechanism where available.

The application should not upload the result to a third-party sharing service.

The user must initiate sharing.

---

# 29. Open URL Action

If the result is classified as a URL:

```text
[ Open Link ]
```

should be displayed.

Before opening:

* validate URL scheme
* show destination where appropriate
* prevent unsafe/unsupported schemes

The application must never automatically open a decoded URL without user interaction.

# 42. Offline Indicator

The scanner does not need a permanent "Offline" warning because offline operation is a core feature.

However, if a feature requires Internet access:

```text

```

should be shown only for that specific feature.

Scanning itself should continue to work.

---

# 43. Error States

Errors must be understandable.

Avoid technical messages such as:

```text
ZXingException: DecodeException
```

Instead:

```text
Couldn't read the barcode.

Try:
• moving closer
• improving lighting
• keeping the barcode steady
• using a clearer image
```

Technical details may be available in developer diagnostics, not normal user-facing UI.

---

# 44. No Barcode Found

Recommended message:

```text
No barcode detected.

Make sure the barcode is:
• visible
• in focus
• well lit
• not covered by glare
```

```text
[ Try Again ]
[ Scan an Image ]
```

# 48. Loading States

Loading indicators should be used only where actual processing is occurring.

Examples:

```text

```

# 49. Success States

Success feedback should be concise.

Examples:

```text
Barcode detected
Copied
Saved to history
```

The UI should avoid excessive animations.

# 50. Accessibility

The application must support:

* screen readers
* keyboard navigation on Web
* visible focus
* semantic controls
* accessible names
* adequate contrast
* sufficiently large interactive targets
* reduced motion
* non-color-only status communication

---

# 51. Touch Target Requirements

Interactive controls should provide sufficiently large touch areas.

Important controls include:

* Scan
* Copy
* Share
* Open
* Torch
* Camera switch
* Image selection
* Back
* Delete

The visible icon may be small, but the interactive hit area must be appropriately sized.

---

# 52. Color Usage

Color must not be the only indicator of state.

For example, do not communicate:

```text
Green = success
Red = error
```

without additional:

* icon
* text
* shape
* status message

---

# 53. Dark Mode

Dark mode must be supported.

Scanner preview considerations:

* overlay must remain visible
* controls must remain readable
* excessive brightness should be avoided
* camera content should remain visually clear

The camera image itself should not be artificially darkened so much that barcode visibility is reduced.

---

# 54. Responsive Design

The application must adapt to:

* small Android phones
* large Android phones
* tablets
* small Web windows
* desktop Web
* high-resolution displays

The scanner should prioritize usable camera preview dimensions rather than forcing desktop proportions onto mobile screens.

# 68. Clipboard Handling

Copying sensitive information should be a deliberate user action.

The application should not automatically copy:

* NID information
* personal identification numbers
* decoded credentials
* private URLs

Clipboard contents should not be retained unnecessarily by the application.

The visual design should be:

* clean
* modern

# 78. History Privacy

History previews should avoid unnecessarily displaying sensitive content.

For example:

```text

```

may be preferable to showing the entire payload in a list.

---

# 79. Data State Indicators

```text

Saved
```

# 80. Interaction Timing

The application should feel immediate.

Avoid unnecessary:

* confirmation dialogs
* loading screens
* animations
* navigation steps
* repeated permission requests

# 81. Error Recovery

Every major error should provide a recovery path.

Example:

```text

 ↓
```

# 82. Offline UX

If the user has no Internet:

```text

History → continues normally
Image scanning → continues normally
Settings → continues normally
```

Only explicitly network-dependent features should show connectivity requirements.

# 87. NID Test Data Policy

Real Bangladesh NID information is highly sensitive.

Therefore:

* Do not commit real NID images to Git.
* Do not commit real NID payloads.
* Do not use real personal information in automated tests.
* Use synthetic or legally authorized anonymized fixtures.
* Keep sensitive test material outside public repositories.

The privacy/security specification will define this in greater detail.

# 99. AI Coding Agent UI Rules

Before implementing UI, the AI coding agent must:

1. Read all four specification documents.
2. Identify the relevant UI requirements.
3. Preserve scanner-first UX.
4. Avoid adding undocumented features.
5. Avoid unnecessary UI complexity.
6. Maintain accessibility.
7. Maintain Android/Web consistency.
8. Keep platform-specific UI behavior isolated.
9. Never expose sensitive data unnecessarily.
10. Never automatically trigger external actions.
11. Never remove error recovery paths.
12. Never hard-code scanner-engine behavior into presentation components.

# 100. Final UX Principle

The application should follow one simple interaction philosophy:

```text
Open
 ↓
Scan
 ↓
Understand
 ↓
Act
```

The user should always know:

* what the scanner is doing
* what it detected
* what the result means
* what action is available
* what data is stored
* when information leaves the device

The interface must remain **simple for ordinary QR/barcode scanning while providing a technically serious and privacy-conscious experience for dense PDF417 use cases, including Bangladesh NID testing.**
