# SCANNER ENGINE VERIFICATION

## Universal QR and Barcode Scanner

**Project:** Universal QR and Barcode Scanner
**Platforms:** Android + Web
**Primary Principles:** Accuracy-First, Privacy-First, Offline-First
**Document Status:** Technology Verification
**Implementation Status:** Not Yet Authorized

---

# 1. PURPOSE

This document defines the process for evaluating and verifying barcode scanning engines before production implementation.

The purpose is to determine whether a candidate scanner engine can satisfy the actual requirements of the project across:

* Android
* Web
* Required 1D barcode formats
* Required 2D barcode formats
* PDF417
* Micro QR where applicable
* Camera input
* Image input
* Offline operation
* Accuracy
* Performance
* Privacy
* Security
* Licensing
* Maintainability

This document does not authorize production implementation.

---

# 2. VERIFICATION PRINCIPLE

A library's documentation is evidence of claimed capability.

It is **not by itself proof of project-level accuracy or suitability**.

The project must distinguish:

```text
Library Claims
      ↓
Platform Capability
      ↓
Integration Feasibility
      ↓
POC Verification
      ↓
Accuracy Testing
      ↓
Production Decision
```

A barcode format must not be marked as fully supported until the relevant implementation has been verified.

# 4. CURRENT EVIDENCE — GOOGLE ML KIT

Google ML Kit's Android Barcode Scanning documentation currently lists support for:

* Code 128
* Code 39
* Code 93
* Codabar
* EAN-13
* EAN-8
* ITF
* UPC-A
* UPC-E
* QR Code
* PDF417
* Aztec
* Data Matrix

The Android API supports bundled and unbundled model delivery. Google also documents image-quality requirements and notes that denser formats such as PDF417 require greater pixel dimensions for reliable reading.

### Important limitation

This evidence establishes **Android support**.

It does not by itself establish that ML Kit provides the required Web implementation.

Therefore:

```text
ML Kit Android
      ↓
Potential Android Candidate
```

but:

```text
ML Kit
      ↓
Universal Android + Web Scanner Engine
```

must not be assumed.

### Additional documented limitation

Google's Android documentation currently notes that Data Matrix recognition requires the code to intersect the center point of the input image, meaning only one Data Matrix code can be recognized in an image under that limitation.

This must be included in project-level testing.

# 7. FORMAT VERIFICATION RULE

For every required format, verify:

1. Library-level support
2. Platform-level support
3. Actual project integration
4. Detection
5. Decoding
6. Correct decoded value
7. Repeatability
8. Difficult-condition behavior

The project must not use this logic:

```text
Library supports format
        ↓
Therefore application supports format
```

Instead:

```text
Library supports format
        ↓
Platform supports format
        ↓
Integration works
        ↓
POC passes
        ↓
Accuracy tests pass
        ↓
Application support
```

# 10. CAMERA VERIFICATION

Scanner-engine verification must not be separated completely from camera verification.

The project must test:

```text
Camera
  ↓
Frame Quality
  ↓
Scanner Engine
  ↓
Detection
  ↓
Decode
```

Poor camera configuration can make a capable decoder appear inaccurate.

Therefore evaluate:

* Resolution
* Focus
* Exposure
* Motion
* Frame rate
* Region of interest
* Orientation
* Lighting
* Distance

# 12. PDF417 VERIFICATION

PDF417 is a critical verification target.

Minimum test categories:

```text
PDF417
├── Normal
├── Small
├── High Density
├── Low Resolution
├── Blur
├── Low Light
├── Glare
├── Rotation
├── Perspective Distortion
├── Partial Damage
├── Camera Capture
└── Image File
```

Google's current ML Kit documentation specifically notes that dense formats such as PDF417 require sufficient pixel dimensions for reliable reading.

Therefore PDF417 testing must record:

* Input resolution
* Approximate barcode dimensions
* Distance
* Lighting condition
* Device/camera
* Time to decode
* Success/failure
* Correctness of decoded payload

---

# 13. BANGLADESH NID-ORIENTED PDF417 TESTING

The project must separate:

### Stage A — PDF417 Detection

Can the engine detect a PDF417 symbol?

### Stage B — PDF417 Decoding

Can the engine return the raw payload?

### Stage C — Payload Integrity

Is the returned payload complete and consistent?

### Stage D — Encoding

Can the character encoding be identified and decoded correctly?

### Stage E — Structure

Does the payload match a verified known structure?

### Stage F — NID Parser

Only after verified structure evidence exists.

### Stage G — Validation

Validate the parsed fields.

### Stage H — Presentation

Present sensitive information safely.

---

# 14. NID SAFETY RULE

The scanner engine must never contain undocumented assumptions about Bangladesh NID data.

Do not infer:

* Field names
* Field order
* Character encoding
* XML format
* Binary format
* Encryption
* Compression
* Checksums
* Personal-data layout

from:

* One sample
* Internet discussions
* AI-generated examples
* Reverse-engineering assumptions
* Unverified third-party claims

NID-specific implementation requires verified evidence.

# 15. MICRO QR VERIFICATION

Micro QR is conditional.

If the selected engine supports Micro QR, verify:

* Detection
* Decoding
* Camera scanning
* Image scanning
* Rotation
* Small-size performance
* Android support
* Web support
* Accuracy

If it cannot be reliably supported across the required platform scope, it should remain conditional or be deferred.

ZXing-C++ currently documents Micro QR support, including its barcode format definitions.

# 16. MULTIPLE BARCODE VERIFICATION

The project must test images containing:

* Multiple QR codes
* Multiple 1D barcodes
* Multiple mixed formats
* Multiple PDF417 codes
* QR + PDF417
* 1D + 2D combinations

The application must not silently select a potentially sensitive barcode when multiple results are available.

# 18. TEST METRICS

Record at minimum:

### Detection Rate

```text
Detected Samples / Total Samples
```

### Successful Decode Rate

```text
Correctly Decoded Samples / Total Samples
```

### False Positive Rate

Cases where a barcode is reported incorrectly.

### False Negative Rate

Cases where a valid barcode is not detected/decoded.

### Decode Latency

Time from usable input to successful decode.

### Repeatability

Whether repeated scans of the same test input produce consistent results.

---

Measure:

* Startup time
* Scanner initialization
* First detection
* Average detection latency
* CPU usage
* Memory usage
* Battery impact
* Frame-processing rate
* Image-processing time

Do not optimize only for speed.

Accuracy must remain a primary constraint.

* Network communication
* Cloud processing

* Analytics
* Device identifiers
* Data collection
* Third-party services

---

# 21. SECURITY VERIFICATION

Test:

* Malformed payloads
* Oversized payloads
* URL payloads
* HTML-like payloads
* Script-like payloads
* Dangerous URL schemes
* Binary-looking data
* Invalid encodings
* Unexpected Unicode
* Repeated scanning
* Multiple barcode payloads

Decoded content must remain untrusted data.

# 33. STOP CONDITION

Stop technology selection and request further investigation if:

* Required PDF417 support is unreliable
* Required formats are missing
* Web support is inadequate
* Android support is inadequate
* Offline operation is impossible
* Privacy requirements cannot be satisfied
* Licensing is unacceptable
* Performance is inadequate
* Accuracy cannot meet the project requirement
* NID-related requirements cannot be responsibly verified

Do not weaken a requirement silently to make a technology fit.
