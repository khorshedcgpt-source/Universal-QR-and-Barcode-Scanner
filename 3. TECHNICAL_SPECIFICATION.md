# 1. Purpose

This document defines the concrete technical technologies, libraries, runtime environments, development standards, scanner engine strategy, storage technology, testing strategy, build strategy, and platform implementation requirements for the Universal QR and Barcode Scanner.

This document converts the architectural decisions from `ARCHITECTURE.md` into implementable technical constraints.

It does **not** replace `PROJECT_SPECIFICATION.md`.

The relationship is:

```text
PROJECT_SPECIFICATION.md
        ↓
Defines WHAT the application must do
        ↓
ARCHITECTURE.md
        ↓
Defines HOW the system is structured
        ↓
TECHNICAL_SPECIFICATION.md
        ↓
Defines WHICH technologies implement that architecture
```

---

# 2. Technical Objectives

The implementation must prioritize:

1. Scanning accuracy
2. Consistent behavior
3. Offline operation
4. User privacy
5. Minimal permissions
6. Fast scanning
7. Low memory usage
8. Maintainable architecture
9. Android and Web compatibility
10. Replaceable scanner engine
11. Testability
12. Long-term extensibility

The application must not sacrifice scanner accuracy merely to simplify implementation.

# 5. Why Capacitor Instead of Tauri

Tauri remains technically viable and supports Android, but this project has a Web-first architecture and does not require a desktop application as a primary target.

Tauri uses Rust for native backend functionality and has additional native/mobile development requirements.

Capacitor is more directly aligned with this project's target:

```text
Primary Web Application
        +
Android Application
        +
Optional PWA
```

Therefore:

**Approved primary choice: Capacitor**

Tauri should not be introduced unless a future requirement specifically justifies it.

# 6. Scanner Engine

## 6.1 Primary Scanner Engine

### ZXing-C++

The primary barcode decoding engine will be:

**ZXing-C++**

Repository:

[ZXing-C++ official repository](https://github.com/zxing-cpp/zxing-cpp?utm_source=chatgpt.com)

ZXing-C++ is a C++ barcode processing library with Android and WebAssembly wrappers/bindings. It supports a broad range of 1D and 2D formats.

---

# 7. Why ZXing-C++

ZXing-C++ is selected because the project requires a scanner engine that can be used across both target environments.

Important advantages:

* Open source
* Multi-format
* Android support
* WebAssembly support
* Broad QR support
* Broad 1D barcode support
* PDF417
* Data Matrix
* Aztec
* EAN/UPC
* Code 128
* Code 39
* Code 93
* Codabar
* ITF
* MaxiCode support
* Thread-safe library design
* Performance-oriented C++ implementation

The current project documentation lists Android and WebAssembly wrappers and a broad supported-format set.

---

# 8. Scanner Engine Architecture

The application must NOT directly couple the UI to ZXing-C++.

The architecture must use an abstraction:

```text
Application
    ↓
ScannerService
    ↓
ScannerEngine interface
    ↓
 ┌──────────────────────┐
 │ ZXing Android Adapter│
 └──────────────────────┘

or

 ┌──────────────────────┐
 │ ZXing WASM Adapter   │
 └──────────────────────┘
```

Example conceptual interface:

```text
ScannerEngine
├── initialize()
├── scanFrame()
├── scanImage()
├── scanMultiple()
├── getSupportedFormats()
└── dispose()
```

The exact TypeScript interface must be defined during implementation.

# 9. Android Scanner Implementation

Android should use:

```text
CameraX
   ↓
Image Analysis
   ↓
Native / JNI bridge
   ↓
ZXing-C++
   ↓
Normalized ScanResult
   ↓
React UI
```

CameraX is recommended by Android for new camera applications and provides an image-analysis use case suitable for computer-vision/scanning workloads.

The native Android layer should avoid unnecessarily passing large image buffers between Java/Kotlin and JavaScript.

Where practical:

```text
Camera frame
    ↓
Native processing
    ↓
ZXing-C++
    ↓
Small structured result
    ↓
JavaScript
```

This reduces unnecessary memory copying.

---

# 10. Web Scanner Implementation

The Web implementation will use:

```text
Browser Camera
     ↓
MediaDevices.getUserMedia()
     ↓
Video/Image frame
     ↓
WebAssembly
     ↓
ZXing-C++
     ↓
Normalized ScanResult
```

The browser's native `BarcodeDetector` API must **not** be the only scanner implementation.

The API is still listed as limited availability and is not supported consistently across major browsers.

It may optionally be used as a future optimization if capability detection confirms that its use does not reduce supported formats or accuracy.

---

# 11. WebAssembly Requirement

The Web scanner engine should use a WebAssembly build of ZXing-C++.

Conceptually:

```text
ZXing-C++ source
        ↓
WebAssembly build
        ↓
scanner.wasm
        ↓
Web Scanner Adapter
        ↓
ScannerService
```

The WASM binary must be treated as an application asset.

It must not be downloaded from a remote third-party server at runtime.

---

# 12. Offline Scanner Requirement

After the application has been installed/loaded and required assets are cached:

**Scanning must not require Internet access.**

Required scanner assets:

* JavaScript bundles
* CSS
* WASM scanner binary
* required models/assets
* application icons
* local configuration

must be locally available.

No remote API may be required for barcode decoding.

---

# 13. ML Kit Position

Google ML Kit Barcode Scanning will **not** be the primary cross-platform engine.

ML Kit remains a technically valid Android-specific alternative and currently supports:

* Code 128
* Code 39
* Code 93
* Codabar
* EAN-13
* EAN-8
* ITF
* UPC-A
* UPC-E
* QR Code
* PDF417
* Aztec
* Data Matrix

However, Android ML Kit and Web would require different primary scanning implementations.

Therefore ML Kit may be evaluated later as:

```text
Optional Android optimization
```

but not as the project's architectural foundation.

# 17. Camera Processing Strategy

The application must not decode every camera frame at maximum resolution.

Preferred pipeline:

```text
Camera
 ↓
Preview
 ↓
Frame sampling
 ↓
Resolution control
 ↓
Scanner
 ↓
Result confidence / validation
```

The scanner must have configurable:

* frame interval
* analysis resolution
* scan region
* supported formats
* duplicate-result suppression

---

# 18. Scan Region

The scanner UI should support a central scan region.

Conceptually:

```text
┌─────────────────────────────┐
│                             │
│                             │
│       ┌─────────────┐       │
│       │             │       │
│       │ SCAN REGION │       │
│       │             │       │
│       └─────────────┘       │
│                             │
│                             │
└─────────────────────────────┘
```

However, the scanner must retain an option to analyze the full frame.

The scan region must be an optimization, not an artificial restriction that causes missed codes.

Image scanning must use the same logical scanner interface:

```text

   ↓

   ↓

   ↓

   ↓
```

Supported input sources should include:

* camera capture
* gallery/image selection
* file upload
* drag-and-drop on Web where supported

The original file must not be uploaded to a server merely to decode a barcode.

# 21. Result Classification

Decoded data must be classified locally.

Potential categories:

* URL
* text
* email
* telephone
* SMS
* Wi-Fi
* contact/vCard
* calendar/event
* geographic coordinate
* payment-related data
* unknown/raw data

Classification must never execute decoded content automatically.

---

# 22. URL Security

A decoded URL must be treated as untrusted input.

Before opening a URL:

1. Parse it.
2. Validate the scheme.
3. Display the destination.
4. Allow user confirmation.
5. Reject unsupported/dangerous schemes.

Allowed default schemes may include:

```text
https:
http:
```

Other schemes must be handled explicitly.

The scanner must never interpret decoded content as executable code.

---

# 23. History Storage

History must be stored locally.

Preferred Web/Android storage technology:

**IndexedDB**

The application should use an abstraction such as:

```text

```

rather than allowing components to directly manipulate IndexedDB.

# 24. IndexedDB Library

A small, mature IndexedDB wrapper may be used.

**Dexie**

However, the application architecture must keep Dexie behind a repository/data-access layer.

This allows future replacement without changing business logic.

# 26. Privacy Requirement

Default behavior:

```text
Camera frame
      ↓
Local processing
      ↓
Result
      ↓
Local history
```

Not:

```text
Camera
 ↓
Cloud server
 ↓
Barcode decoding
```

No barcode data, image, camera frame, or scan history may be transmitted to a remote server unless a future feature explicitly introduces such functionality and obtains appropriate user consent.

---

# 27. Network Policy

The core scanner must function without network access.

Network access may be used only for explicitly user-requested functions such as:

* opening a URL
* downloading user-requested content
* future optional update functionality

Network availability must never determine whether the scanner can decode a barcode.

# 37. Accuracy Testing

Scanner accuracy must be measured using a reproducible test set.

Important dimensions:

* successful decode rate
* false positives
* time to first successful decode
* multiple barcode detection
* rotated codes
* damaged codes
* low-quality images
* different camera distances
* different lighting conditions

Performance claims must be based on measurements.

---

# 38. Duplicate Scan Suppression

The scanner must not create dozens of identical history records when the same barcode remains in the camera frame.

The scanner should implement:

```text
Result
 ↓
Normalize
 ↓
Compare with recent result
 ↓
Suppress duplicate
```

The exact suppression interval must be configurable.

---

# 39. Performance Requirements

The application should:

* avoid unnecessary frame processing
* avoid unnecessary React re-renders
* release camera resources when not scanning
* release image buffers promptly
* avoid retaining large image objects
* avoid storing unnecessary binary data
* lazy-load non-scanner features where practical

---

# 40. Memory Requirements

The application must avoid:

* full-resolution frame retention
* unlimited scan history
* unnecessary image caching
* duplicate WASM instances
* repeated scanner initialization

Scanner engine lifecycle must be explicit:

```text
initialize()
 ↓
scan
 ↓
pause
 ↓
resume
 ↓
dispose()
```


```text

```

```text

   ↓
```

```text
   ↓
User guidance
```

# 76. Technical Acceptance Criteria

The technical architecture will be considered implemented when:

### Web

* Application runs without backend
* Camera scanning works where browser permissions allow
* Image/file scanning works
* Scanner operates offline after required assets are available
* History is stored locally
* ZXing-C++ WASM is used
* Barcode data is not uploaded for decoding

### Android

* Capacitor Android application builds
* Camera permission works correctly
* CameraX provides image analysis
* ZXing-C++ is used through the Android scanner adapter
* Scanning works without Internet
* History is stored locally
* Camera resources are released correctly

### Architecture

* UI does not directly depend on native scanner APIs
* Scanner engine is replaceable
* Platform-specific code is isolated
* Scan results use a shared domain model
* Scanner test fixtures exist
* Errors are normalized
* No mandatory backend exists
